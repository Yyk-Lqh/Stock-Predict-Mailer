# 专业模式设计

参考对象：Dify 的工作流编排、Coze 的节点画布、RAGFlow 的流程与运行面板。

本文只写**能落地的部分**和**明确不做的部分**。专业模式不是第二个 Dify：它表达的是本轮分析任务的结构，提交时仍然走既有的分析任务接口，图本身不执行。

## 参考产品的共同结构

四个区域几乎是一致的选择：

| 区域 | Dify | Coze | RAGFlow |
| --- | --- | --- | --- |
| 左 | 节点库（分类、搜索） | 节点面板（添加/拖入） | 组件面板 |
| 中 | 从左到右的有向图，贝塞尔连线 | 自由画布，节点卡片带端口 | 画布 + 节点配置 |
| 右 | 节点配置面板 | 节点设置浮层 | 参数表单 |
| 下 | 运行日志 / 调试结果 | 试运行面板 | 运行记录抽屉 |

再往深一层，它们共有三个能力：**变量引用**（`{{#node.field#}}`）、**单步调试**（只跑选中节点）、**服务端存储**（工作流是资源，不只是本地文件）。

## 本项目的硬约束

这三条决定了哪些能抄、哪些不能：

1. **图不执行。** 分析任务由既有接口按固定阶段执行，画布只是它的可视化与编辑面。任何"点一下就发请求/跑节点"的设计都不做——那会绕开任务治理、授权与失败记录。
2. **单文件打包 + 体积预算。** 控制台是零构建的原生 JS，`memory.js` 由 `scripts/build_console.py` 拼接，预算被脚本卡住。引入图形库（React Flow 之类）不在选项内。
3. **只有本机。** 工作流存在 `localStorage`，没有服务端资源、没有多用户、没有版本历史。

## 本次落地

- **左侧节点库**：十个节点类型按色彩点区分，点一下即在该处新增对应类型的节点，并自动带上该类型的默认标题与说明；位置沿用"选中节点右侧 248px"的既有规则，选中节点不会被遮住。
- **节点卡片**：左侧 3px 类型色条、左右两端端口圆点、状态徽标与来源保持原样。端口目前是**视觉元素**，连线仍走检查器里的表单（见下表）。
- **已训练模型节点**：节点库的「已训练模型」读取 `GET /api/registry`，把注册表里最新的可见版本接成一个节点，标题为「算法 · 版本前 8 位」，详情写训练行数与标签截止；`modelVersion` 存进工作流，卡片 `title` 给出完整版本号。接入的是**声明**，不触发推理——预测仍走 `model-predict`。
- **布局**：普通桌面下为三栏（节点库 / 画布 / 检查器）；专业视图下节点库与检查器都浮在画布上，左右各一列，中间留出画布。

## 与参考产品的差距

| 能力 | 现状 | 为什么没做 |
| --- | --- | --- |
| 拖拽连线 | 检查器里选源/目标 | 端口命中区域、连线预览、撤销粒度都要重做；现有 `canConnect` 已挡住自连、重复与环，先复用这套校验 |
| 运行日志面板 | 复用任务进度与报告区 | 已经有真实事件流，再叠一层日志会出现两个真相 |
| 变量引用 | 无 | 图不执行，没有运行期变量可引用 |
| 单步调试 | 无 | 同上：单步执行等于绕开任务治理 |
| 服务端存储 | 仅 `localStorage` + 导入导出 | 需要工作流表、版本与权限；属于独立一片，不是 UI 改动能顺带完成的 |
| 小地图 | 无 | 画布尺寸有限，价值低于维护成本 |

## 后续候选（按价值排序）

1. **拖拽连线**：端口 pointerdown → 临时路径 → 命中目标端口 → 复用 `canConnect` 落库。
2. **服务端存储**：`workflows` 表 + `GET/PUT /api/workflows/<id>`，带 revision 防覆盖；导入导出保留为离线通道。
3. **节点右键菜单**（复制、删除、禁用）：比检查器里的按钮快，但要处理与拖拽的事件冲突。

任何一项落地前都要先解决同一件事：**在没有自动化浏览器的情况下，怎么验证拖拽交互**。目前这类改动只能靠人工在开发者工具里跑 `tests/browser_*.js`。
