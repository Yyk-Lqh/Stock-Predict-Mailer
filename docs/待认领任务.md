# 待认领任务

本清单把《模型能力下一步实施计划》与《实施阶段与验收》里尚未完成的工作，拆成可独立认领、可独立验收的条目。认领前请在 issue 中说明方案，并确认没有人在做同一项。

任务状态以 issue 为准；本文件只描述范围与验收口径，不代表承诺工期。所有条目都遵守 [CONTRIBUTING](../CONTRIBUTING.md) 的代码约定。

## 当前状态（0.5.0）

C、D、E 报告侧、F-1 至 F-3、G-1 已在 0.5.0 完成，验收见《阶段验收记录》。仍未开始的是邮件发送（用户明确推迟）、生成 API 实际调用、共享服务隔离与多用户认证，以及可选的 G-2、G-3。

## 优先级与依赖

```text
H-1 邮件发送闭环 ── 依赖 H-2 报告格式定稿；与 E 的报告侧已接通
H-2 报告邮件版式与收件人配置
H-3 生成 API 实际接入 ── 依赖供应商与允许清单，机制已在 0.5.0 就绪
H-4 共享服务隔离与多用户认证 ── 与 principal 语义变更耦合，需先改文档
H-5 真实行情采集端 ── 机制已在 0.5.0 就绪，缺数据源与授权
H-6 GitHub Ruleset 启用 ── 纯仓库设置，无代码依赖，优先级最高
```

## 条目

| 编号 | 任务 | 难度 | 前置 | 验收要点 |
| --- | --- | --- | --- | --- |
| H-1 | 邮件发送闭环 | 中 | H-2 | 默认只预览不发信；显式确认才发送；重跑不重复建邮件；失败不静默成功 |

## 不适合作为首个 PR 的条目

H-4、H-5 涉及身份语义与真实数据授权，需要先在设计 issue 中达成一致。H-6 是纯仓库设置，改动最快且收益最高，建议第一个做。

## 提交方式

1. 在本仓库开 `认领任务` issue，写清编号与方案；
2. fork 后从 `main` 切分支；
3. 按 CONTRIBUTING 跑完四项检查；
4. 提 PR，模板中勾选边界自查。
