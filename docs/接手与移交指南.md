# 接手与移交指南

给"要接手这个仓库的人"看的路线图，也给"要交出去的人"当交割清单。区别于 [CONTRIBUTING](../CONTRIBUTING.md)：贡献者只需要提一个 PR，接手者要能独立判断"什么算完成、什么不能宣称、下一步该做什么"。

一句话概括：**接手 = 在你自己机器上跑通并验证一次 + 接受五个已经定死的决定 + 拿到不走 Git 的那部分资产 + 认清现在真正卡住的不是代码。**

## 0 先建立正确预期

| 项目事实 | 含义 |
| --- | --- |
| 单用户、本机运行的研究工具 | 没有服务端、没有登录、没有多租户；不要按 Web 产品的思路理解 |
| 约 4400 行 Python、74 个受版本控制的文件 | 一天能读完核心，不是靠人海维护的体量 |
| 50 项测试、约 40 秒 | 反馈很快，改动前先跑一遍，改动后必须仍然全绿 |
| 依赖 7 个（numpy / scikit-learn / scipy / duckdb / pyarrow / openpyxl / cryptography），LightGBM 是可选 extra | 环境很轻，装不上通常是网络或 wheel 平台问题，不是项目复杂 |
| 上传页面是 `http.server` + 原生 JS | 没有前端框架，没有构建步骤，改样式直接改 `src/stock_predict_mailer/web/` |
| 存储是 workspace 下的 SQLite + 文件目录 | 没有独立数据库服务，备份=复制目录 |

**它不是**：实盘交易系统、可对外的 API 服务、已验证有预测能力的模型。任何对外表述都要守住这条线（见 README「使用边界」）。

## 1 接手的三个层次，缺一层都不算交接完

| 层次 | 内容 | 判定 |
| --- | --- | --- |
| 代码 | GitHub 仓库（public, MIT） | `git clone` 后能跑通测试 |
| 运行状态 | 本机 `data/local` 下的快照、模型、实验、报告 | 能重新生成，其中**私钥不可再生** |
| 非代码资产 | 数据授权与来源、SMTP 凭证、GitHub Admin、对外承诺过的话 | 有书面移交记录 |

只有第一层是自然的。第二、三层必须由交出方主动交接，见第 6 节。

## 2 第一小时：跑通，并确认"真的跑通"

```powershell
git clone https://github.com/Yyk-Lqh/Stock-Predict-Mailer.git
cd Stock-Predict-Mailer
uv sync --extra trees --extra dev
uv run python -m unittest discover -s tests -q
```

四项判据，全部满足才算跑通（缺一项说明环境或平台有问题，不要急着读代码）：

1. `Ran 50 tests ... OK`，没有 skip。有 skip 通常意味着 LightGBM 没装上。
2. `uv run ruff check src tests scripts` 输出 `All checks passed!`。
3. `python scripts/check_repo_hygiene.py` 通过（它检查有没有把数据、密钥、模型包误提交）。
4. 端到端冒烟：

```powershell
uv run stock-mailer --config config/example.toml init
uv run stock-mailer --config config/example.toml demo-run --cutoff 2026-10-24T20:00:00+08:00 --trees
```

输出里应当有快照 ID、实验 ID、报告 ID、邮件队列 ID，且**不发信**。

注意：clone 下来是**空运行环境**——`data/`、`models/`、`*.log`、`*.sqlite3` 全被 `.gitignore` 排除。`data/local` 里没有别人的历史数据是正常的，`demo-run` 会重建一套合成数据。不要把本地已有数据当成"仓库自带的样例"，也不要为了让它跑起来而把 `data/` 加进版本控制。

## 3 第二天：读代码的顺序

按"每个文件回答什么问题"排，不要按目录字母序读。前六个文件读完，你就掌握了全部不可违反的规则；其余都是外围功能。

| 顺序 | 文件 | 行数 | 它回答的问题 |
| --- | --- | --- | --- |
| 1 | `src/stock_predict_mailer/core.py` | ~120 | 配置怎么加载、workspace 怎么定、`runs` 表怎么记账、`atomic_write` 为什么带重试 |
| 2 | `contracts.py` | ~110 | `contract_id` 怎么算出来的、为什么改一个字段就等于换模型 |
| 3 | `data.py` + [数据契约](数据契约.md) | ~140 | 快照怎么生成、不可变体现在哪、九字段是什么 |
| 4 | `dataset_auth.py` | ~90 | 数据能不能被用来训练，谁说了算；最短，但一行都不能删 |
| 5 | `model_registry.py` | ~285 | 训练/评价/发布/选择/预测的状态机与目录布局，owner 命名空间如何隔离 |
| 6 | `model_training.py` + `training_child.py` | ~640 | 私有训练队列：子进程、阶段进度、取消、超时、心跳；**最复杂，放最后** |
| 7 | 外围（可选） | — | `intake*.py` 接入清洗、`knowledge.py` 检索、`report.py` 报告、`delivery.py` 邮件、`research.py` 旧研究入口 |

配套关系：第 1 步看 `tests/test_core.py`，第 4 步看 `tests/test_model_training.py` 里的授权用例，第 5–6 步看 `tests/test_model_registry.py` 与 `tests/test_model_training.py`。**测试是这个项目最准的规格说明**，文档和注释有歧义时以测试为准。

入口只有两个，先认路：

- `cli.py` 的 `main()`：一个 `argparse` 大分发，模板是 `with tracked_run(cfg, 命令名): ... print(json.dumps(result))`。所有命令都是"跑一次、记一条 run、打印 JSON"。
- `model_cli.py` 的 `add_commands` / `dispatch`：模型相关 18 个命令集中在这里，加新命令只需要在这两个函数里各加一处。

## 4 第三天：跑通模型链路

按这个顺序走，每一步都有门禁，跳过任一步都会报错——报错本身就是理解设计的入口。

```powershell
# 契约检查
uv run stock-mailer contract-check config/task-demo.json

# 阶段 A：固定契约训练（合成数据，自动视为允许平台训练）
uv run stock-mailer model-train <snapshot_id> --contract config/task-demo.json --cutoff <iso>
uv run stock-mailer model-evaluate <model_version> <snapshot_id> --cutoff <iso>
uv run stock-mailer model-publish <model_version> --evaluation <evaluation_id>
uv run stock-mailer model-select <model_version> --allow-demo
uv run stock-mailer model-predict <snapshot_id> --cutoff <iso> --allow-demo

# 阶段 B：签名包（私钥留在本机，公钥交出去）
uv run stock-mailer model-keygen
uv run stock-mailer model-export <model_version> --output <打包路径>
uv run stock-mailer model-install <包路径> --trust-key <独立获得的公钥>

# 阶段 C：授权 → 队列 → 比较 → 显式切换
uv run stock-mailer dataset-auth <snapshot_id>
uv run stock-mailer dataset-authorize <snapshot_id> --platform --note "已确认数据权利"
uv run stock-mailer train-submit <parent_version> --snapshot <snapshot_id> --cutoff <iso>
uv run stock-mailer train-worker --once
uv run stock-mailer train-status <job_id>
uv run stock-mailer model-compare <candidate> --baseline <parent> --snapshot <snapshot_id> --cutoff <iso>
uv run stock-mailer model-select <model_version> --confirm-personal
uv run stock-mailer model-predict <snapshot_id> --cutoff <iso> --allow-personal
```

完整参数与拒绝条件见 [平台模型命令与验收](平台模型命令与验收.md)。两个容易误解的点：

- 训练**不会**自动发布，比较**不会**自动切换，切换**不会**自动预测——三处都是刻意的显式确认。
- `zero` / `momentum` 是基线算法（`model-train --algorithm`），用来证明"模型比什么都不做更好"，不是可选模型。

## 5 必须接受的五个既有决定

这些不是风格偏好，是已验收的行为契约。想改必须开 issue 并升版本，不要在 PR 里顺手改。

| 决定 | 为什么 | 违反的后果 |
| --- | --- | --- |
| 契约是哈希锁定的 | `contract_id` = 契约内容哈希；特征顺序、股票池、标签周期、基准任一改动都会换 ID | 旧模型全部不兼容，历史报告无法复现 |
| 推理路径不碰 pickle | 只加载 Ridge 系数 JSON 与 LightGBM 原生文本，预测时不调用 `fit` | 引入反序列化执行风险，等于把"只读推理"变成任意代码执行 |
| `principal` 不是认证 | 它是本机受信配置项，上传服务只监听 `127.0.0.1` | 一旦对外暴露或让用户自填 owner，隔离形同虚设 |
| 训练授权不可绕过 | 用户导入数据默认禁止平台训练，需 `dataset-authorize --platform --note` 显式授权 | 等于未经许可用他人数据训练，这是产品红线不是技术细节 |
| 失败必须显式且不改状态 | 训练失败/取消/超时都保留错误类别，不产生版本、不覆盖旧版本、不改当前选择 | 静默失败会让"没换模型"被误读为"换了但没变好" |

另外两条工程约束：**测试必须同时在 Windows 与 Linux 通过**（文件替换、时区、路径大小写行为不同），**文档与代码同 PR 同步**（`CHANGELOG` / `docs/阶段验收记录.md` / 相关专题 / README 受影响处）。

## 6 不走 Git 的交接清单

以下东西**永远不会出现在仓库里**，必须单独移交，否则接手方接到的只是"能跑 demo 的空壳"。

- [ ] **模型签名私钥**：`<workspace>/secrets/model-signing/`。丢了不影响已发出的包被验证（公钥仍在），但无法再以同一发布者身份签名新包，只能换发布者。
- [ ] **真实数据来源与授权凭证**：向谁买的、许可范围是否允许训练/再分发、到期时间。这决定了能否碰阶段 6B 与 D/F 系列任务。
- [ ] **SMTP 参数**：走环境变量，不入库不入配置。没移交就只能停在邮件预览。
- [ ] **GitHub 仓库 Admin**：合并权限、tag 发布、Ruleset 与 Secret scanning 设置。仅给 Write 不算完整移交。
- [ ] **tag 与发版惯例**：当前 `v0.4.0` 是附注标签，指向 CI 全绿的提交；发版前必须确认该提交 5 个 job 全绿。
- [ ] **`data/local` 现状说明**（可选）：快照与实验结果可重建，但"哪些结论曾对外说过"不可重建，需口头或书面交代。
- [ ] **已知的不可宣称事项**：哪些数字是合成数据得出的、哪些是成本诊断而非回测。README 与各专题文档的「使用边界」章节是底线，不要在新的对外材料里升级表述。

## 7 会绊倒新人的坑

都是真实踩过的，按遇到概率排序：

1. **换了 `principal` 就"丢模型"**。owner 命名空间是 `sha256(principal)`，改配置里的 `principal` 会让此前训练的个人版本全部不可见。接手时保持 `principal = "owner"`，或明确迁移 `registry/personal/<旧哈希>/` 目录。
2. **clone 后以为项目坏了**。`data/` 不存在、`status` 无输出、`snapshot xxx` 报找不到，都是正常现象，先跑 `demo-data` 或 `demo-run`。
3. **只在 Linux 跑测试就提 PR**。`atomic_write` 的 `os.replace` 在 Windows 上会被并发读短暂锁住，项目为此加了有界重试；只测一个平台等于没测。
4. **手动改 `uv.lock` 或放宽版本范围**。锁文件是 CI 复现的基础，改依赖请用 `uv add/remove` 并说明理由。
5. **以为 synthetic 通过就是功能完成**。合成数据只能验证链路，不能验证效果；`docs/阶段验收记录.md` 严格区分这两件事。
6. **给上传页面加训练或模型执行入口**。上传服务是回环地址上的数据入口，不是控制台，扩权会破坏第 5 节的红线。
7. **CI 里用移动主版本标签引用 GitHub Action**。`astral-sh/setup-uv` 自 v7 后不再发布移动主标签，必须固定到具体 release（现为 `v10.3.2`）。
8. **看附注标签时以为指错了提交**。`/git/ref/tags/<name>` 返回的是标签对象，要再解引用一次才是提交；用 `git rev-parse v0.4.0^{commit}` 更省事。

## 8 现在真正卡在哪

代码不是瓶颈，**数据和授权是**。当前状态（详见 [实施阶段与验收](实施阶段与验收.md) 与 [阶段验收记录](阶段验收记录.md)）：

- 已完成：阶段 1–5、6A、模型阶段 A/B/C（第一批）。
- 缺真实数据：6B 需要授权行情、公司行动、真实交易日历、十交易日影子运行 —— 四项都不是写代码能解决的。
- 未开始：残差适配、多 worker、保留策略、LightGBM 继续训练、生成 API、stable 发布、邮件闭环。

所以接手后**不要**先加功能。先把 50 项测试与 demo 链路在自己机器上复现一遍，再决定是补工程（G 系列、C-3、C-4）还是推动数据落地（F 系列）。方向选择比代码速度重要得多。

## 9 前两周建议做什么

按"能独立完成且不会踩到契约"排序，对应 [待认领任务](待认领任务.md)：

1. **G-1 跨平台差异用例补强**——最安全，并且能强制你把 `atomic_write`、时区、路径行为读透。
2. **C-3 训练产物保留策略**——有明确边界（已选/已发布版本不能被清理），适合建立对命名空间的理解。
3. **C-4 比较的分组与多重比较提示**——需要读懂 bootstrap 那段，但不改模型格式。
4. **文档校正**——拿真实操作对照文档，凡是不准的地方都是高价值 PR。

明确不建议作为第一个 PR：C-1（残差适配）、D-1（继续训练）、E-1（生成 API）、F-1/F-2/F-3（真实数据与 stable），它们涉及契约、模型格式或数据授权，需要先在设计 issue 上达成一致。

## 10 交接完成判定清单

双方一起过一遍，全部打勾才算交接完成：

- [ ] 接手方独立 clone 并跑通：50 项测试 OK、ruff 干净、hygiene 通过、`demo-run` 产出四个 ID。
- [ ] 接手方能解释 `contract_id` 由什么决定，以及为什么改特征顺序是破坏性变更。
- [ ] 接手方能独立走完阶段 C：授权 → `train-submit` → `train-worker` → `model-compare` → 显式切换。
- [ ] 接手方能说出"为什么不能把 `principal` 当认证"和"为什么推理不用 pickle"。
- [ ] 私钥、数据授权、SMTP、GitHub Admin、tag 惯例已书面移交。
- [ ] 接手方知道当前对外**不能**宣称什么，以及哪些结论来自合成数据。
- [ ] Ruleset 已确认：`main` 禁止直推、必须 PR、必须 5 项检查通过。
- [ ] 双方约定下一次同步检查的时间点，以及回滚方式（回退到 `v0.4.0` 这个已知全绿的提交）。
