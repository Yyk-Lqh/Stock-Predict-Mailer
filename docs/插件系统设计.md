# 插件系统设计

状态：三个扩展契约、声明式 manifest、静态白名单注册表。行情侧已收编腾讯、新浪（默认链）与东方财富（可选，需在 `market.json` 的 `sources` 中显式启用）；
报告侧已收编 HTML 与纯文本两个渲染器。通知渠道**目前只有契约**，注册表为空；原因见第 10 节。AKShare、Tushare 等第三方源未接入。

## 1. 目的与非目标

目的：让行情源、报告渲染方式、通知渠道可以在不动任务契约的前提下增加，并让"增加了什么、能做什么"在一条命令里看得到。

非目标，且明确不做：

- 不做运行时加载第三方代码的插件市场。没有 `importlib` 扫目录、没有 entry points、没有从配置读模块路径。
- 不做插件热重载。新增插件需要重启进程，这是有意的；配置（`market.json` 的 `sources`）例外，见第 8 节。
- 不让插件进入推理路径或特征计算。插件只消费已有数据，不定义数据契约。
- 不做沙箱。见第 6 节关于"评审规则 ≠ 运行时强制"的说明。

## 2. 为什么不采用 cordis

曾考虑 [cordiverse/cordis](https://github.com/cordiverse/cordis)。结论是不采用，理由留档以免重复讨论：

1. **运行时错配。** cordis 是 Node.js/TypeScript 元框架，依赖 yarn、vitest 与自己的构建链。本项目是单 Python 运行时（`uv` + hatchling + ruff + 标准库 `unittest`），仓库内没有 `package.json`。引入即意味着两个运行时、两个 lockfile、两套 CI 矩阵，以及 Python 核心与插件宿主之间的 IPC。
2. **版本成熟度。** 复核时最新发布为 `v4.0.0-rc.13`，README 自述接口未稳定。本项目把 `contract_id` 锁死、拒绝约定漂移，把插件接口建在一个 RC 上与之直接冲突。
3. **问题不对口。** cordis 解决的是 JS 应用内插件的依赖注入、生命周期与自动清理。本项目的插件需求是"在契约哈希锁定和三种用途授权下扩展数据源与出口"，属于审计与边界问题，不是依赖注入的易用性问题。
4. **与已写下的产品边界冲突。** [平台基础模型与用户自主训练方案](平台基础模型与用户自主训练方案.md)明确"不接受用户自定义训练脚本、可执行插件或任意序列化模型"。cordis 的核心能力正是运行时加载第三方包。

若将来要做面向外部第三方的 Node 插件市场，那是另一个产品的架构决定，与这个仓库无关。

## 3. 三个契约

插件是普通对象，只要结构上满足某个契约即可，不继承基类、不注册钩子。定义见 `src/stock_predict_mailer/plugins/contract.py`。

| 契约 | 方法 | 约束 |
| --- | --- | --- |
| `DataSourcePlugin` | `quotes(instruments, timeout) -> list[dict]` | 只读网络；返回逐标的报价，数量必须与请求一致；可选 `candles(symbol, timeout)` |
| `ReportRenderer` | `render(view) -> bytes` | 视图仅含 `analysis`、`timezone`、`charts`；自身不发起网络请求、不写文件 |
| `Notifier` | `send(message) -> Mapping` | 只管一次投递；重试、幂等与状态机仍归 `mail_core`。**尚无实现，见第 10 节** |

渲染器与通知渠道的契约已经定下，但没有实现，也没有注册项。空表是事实，不是待办占位。

## 4. manifest 与静态白名单

`declare()` 在**类定义期**构造并校验 manifest，因此声明写错会在 import 时直接失败，而不是等第一次调用。

校验项：`api_version` 必须等于当前版本；`id` 匹配 `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`；`kind` 属于三种用途之一；`label` 不超过 40 字；`capabilities` 非空、不重复、且必须属于该用途允许的能力；`requires` 只能写模块名，且**必须同时给出 `extra` 名称**——否则无法告诉使用者正确的安装命令。

注册表在 `src/stock_predict_mailer/plugins/registry.py`，是一张写死的表：

```python
BUILTIN = Registry((TencentSource(), SinaSource()))
```

`Registry` 只回答表里的 id。安装一个包、放一个文件、设一个环境变量，都不足以成为插件。这就是进程内扩展的全部安全模型，刻意做得很笨。

## 5. 两层信任边界

| 类别 | 落点 | 理由 |
| --- | --- | --- |
| 行情源薄适配、报告渲染、通知渠道 | 进程内，静态白名单 | 代码随包发布、经代码评审，且不接触契约 |
| 带重依赖或来源可疑的采集端 | `src/mcp_server/`，进程外 | 边界已存在，协议已版本化，语言无关 |

重依赖不进核心 `dependencies`，只进 `optional-dependencies`。当前 `crawler` extra 已包含 `pandas`、`requests`、`baostock`；未来的 AKShare、Tushare 适配器应挂在该 extra 下，并在 manifest 的 `requires` 中声明模块名。

## 6. 失败语义

插件失败一律显式返回，不降级、不跳过：

| 情形 | 错误码 | 行为 |
| --- | --- | --- |
| id 不在白名单 | `PLUGIN_NOT_FOUND` | 拒绝，提示只接受内置 id |
| 用途不符 | `PLUGIN_KIND_MISMATCH` | 拒绝，指出实际用途 |
| 接口版本不符 | `PLUGIN_INCOMPATIBLE` | 拒绝，指出双方版本 |
| 声明的能力没有实现 | `PLUGIN_INCOMPATIBLE` | 注册期即失败，不进入注册表 |
| 缺可选依赖 | `PLUGIN_MISSING_DEPENDENCY` | 拒绝，给出模块名与 `.[extra]` 安装命令 |

`resolve_all(kind)` 逐个 `resolve`，因此**不会静默丢掉一个不可用的插件**——行情回退链要么完整，要么在构造时明确报错。

渲染器"不做 IO"是**评审规则，不是运行时强制**。Python 进程内无法在不引入沙箱的前提下阻止一次 `urllib` 调用；把这句话说成"已隔离"是不诚实的。需要强隔离的插件属于 MCP 进程边界。

## 7. 必须继承的不变量

插件不得触碰以下任何一条，违反即视为缺陷而非用法问题：

1. 不改 `contract_id`，不声明特征顺序，只消费 `FEATURE_ORDER`。
2. 不进推理路径：预测时永不调用 `fit`，`training_performed=false` 照旧如实输出。
3. 不重写旧快照、旧报告：插件产物是新记录。
4. 失败不静默：见第 6 节。

## 8. 已收编的行情源与默认链

`plugins/builtin/market.py` 提供 `TencentSource`（`quotes` + `candles`）与 `SinaSource`（`quotes`），都是薄适配器：HTTP、解码和"拒绝不合理报价"的校验仍留在 `control.market_feed.py`，那里依旧是显示契约的唯一所有者。

`plugins/builtin/eastmoney.py` 是另一种形态：自带 URL、数值校验与解析器，不引用 `market_feed` 的私有函数。它是第三方源的样板——插件若借用别的模块内部实现，就只是名字上的插件。

`MarketFeed` 的默认源与默认 K 线源改为从注册表取，回退顺序仍是腾讯在前、新浪在后。既有行情墙测试未修改即通过，说明显示行为没有变化。

### 默认链与可选源

`DEFAULT_MARKET_SOURCES = ("market_tencent", "market_sina")` 是**唯一**会被默认联系的一组源。声明一个新源不会把它塞进这条链：

```python
BUILTIN = Registry((TencentSource(), SinaSource(), EastmoneySource(), TextReport(), HtmlReport()))
```

理由很实际：如果新源靠"注册即生效"，任何没装对应可选依赖的人都会在构造 `MarketFeed` 时直接失败，行情墙跟着挂掉。**声明**（`plugins-list` 里看得到）与**启用**（真的会发请求）必须是两件事。

要启用别的组合，在 `data/agent-local/market.json` 里写 `sources`：

```json
{"sources": ["market_eastmoney"]}
```

校验口径**刻意不一致**：`instruments`、`refresh_seconds`、`enabled` 写错会回退到四个默认指数，因为它们只影响画什么；`sources` 写错直接抛错——它决定进程会联系哪些外部端点，静默换成另一个源属于"没人告诉你"的那类错误。未知 id 抛 `PLUGIN_NOT_FOUND`；重复、非字符串、空列表或超过 4 个抛 `ValueError`。

选中的源里必须有一个声明了 `candles`，否则概览图无法绘制并显式报错。目前腾讯与东方财富都具备该能力，新浪没有——只选新浪会明确失败，而不是悄悄少一张图。

### 改动前先体检，运行中会自动重载

启动时是严格的：`sources` 写错会让大厅起不来，所以先跑只读命令：

```shell
uv run stock-predict-mailer plugins-check --market data/agent-local
```

不联网，只回答三件事：每个插件是否可用、选中的链能否逐个解析、这条链里谁提供日线。有问题时退出码为 2 并给出具体原因（未知 id、重复、缺可选包、没有 candles 源）。不加 `--market` 时检查默认链。

运行中相反：`payload()` 每次比对 `market.json` 的 mtime 与大小，变了就重建源链、丢弃旧快照；新文件无效时保留上一组源，原因写进返回的 `detail` 字段。`enabled: false` 也会丢弃快照——关闭中继后继续展示上一份报价，等于把旧数据当成实时行情。**配置可以重载，代码不行**——新增插件仍需重启进程，这是第 1 节写明的非目标。

`plugins-list` 给出声明清单，其中 `default_chain` 与每个行情源的 `default` 标记说明"哪些真的会发请求"；`plugins-check` 回答"按我现在的配置，大厅能不能起来"。

## 9. 报告渲染器

排版代码从 `agent_service/reporting.py` 搬到 `plugins/builtin/report.py`：一个共享的 `lines()` 句子构建器，加两个只负责格式化的渲染器——`report_text`（纯文本）与 `report_html`（转义、图表 SVG、`cid:` 邮件内嵌图引用）。

`reporting.render()` 保留原签名与返回结构，内部改为向注册表要两个插件再解码，因此调用方、冻结的邮件正文和既有断言都不需要改动。内容仍然只来自分析契约：渲染器决定"怎么读"，不决定"说什么"。

### 来源记录

`save_report` 在报告目录里多写一个 `renderers.json`：

```json
{"plugin_api_version": 1, "release": "0.6.0",
 "renderers": [{"format": "text", "id": "report_text", "module": "…builtin.report", "module_digest": "b5e3…"},
               {"format": "html", "id": "report_html", "module": "…builtin.report", "module_digest": "b5e3…"}]}
```

`module_digest` 是插件所在**模块文件**的 sha256，不是类的指纹。两个插件写在同一个文件里（`report_text` 与 `report_html` 现在就是）会共享同一个指纹——这一点明说，而不是假装精确，所以每项同时给出 `module`。它的用途只有一个：回答"这份报告是哪个版本的排版代码产出的"，配合 `plugins-list` 里当前运行的指纹做比对。

来源由新增的 `render_with_provenance()` 提供，`render()` 仍是两返回值。

## 10. 通知渠道为什么仍是空的

`mail_core/transports.py` 里已经有一个结构匹配的 `Transport` Protocol 和三个实现（`FileTransport`、`SMTPTransport`、`MCPTransport`），`deliver()` 还会显式校验 `transport` 只允许 `file` / `smtp`——不存在"拼错就悄悄走 SMTP"的路径。

问题在于它们不是无状态插件：`SMTPTransport` 的构造需要本次消息的 analysis（用来拒绝 Mock 报告）、SMTP 设置与凭据环境变量；`MCPTransport` 需要绑定好的调用器与工具名。一个 `send(envelope, payload)` 的 manifest 契约表达不了"先用消息上下文构造、再投递一次"这件事。

硬套的结果是给一个已经正确、已被测试覆盖的层再加一层工厂壳，除了让 `plugins-list` 多两行没有任何收益。这与第 2 节拒绝 cordis 的理由是同一条：不为架构整齐而增加接缝。

真正值得插件化的是**新增**的渠道（企业微信机器人、钉钉、Server 酱），它们是无状态的"POST 一段 JSON"。届时把契约定为 `build(settings) -> Transport` 的两段式再接进来。在那之前，`notifier` 表为空是准确描述，不是待办占位。

## 11. 未完成

- 通知渠道：见第 10 节，等第一个无状态渠道落地时再定两段式契约。
- 第三方数据源：东方财富已接入，但它与腾讯、新浪一样只是公开行情页的只读中继，无授权、无 SLA，**仍不是任务采集端**。AKShare、Tushare、巨潮等未接入。
  AKShare 不适合放进进程内插件层：它内部用 requests 且不接收我们的超时参数，而 `MarketFeed.payload()` 跑在 HTTP 请求路径上，一次挂起的连接会拖住整个接口。这类"带重依赖、又无法约束执行时间"的源应走 `src/mcp_server/` 的进程边界，而不是 `quotes()` 契约。
- `requires` / `extra` 这条路径仍只有测试覆盖：三个已收编的源都不依赖可选包，东方财富只用标准库。接入 AKShare 这类重依赖源时才会第一次真实走到它。
- 审计只覆盖报告侧：`renderers.json` 记下排版来源，但行情源与通知渠道没有使用记录，也没有统一的插件调用日志。
- 未做多进程或跨用户隔离；`principal` 仍是本机标识，不是登录身份。
