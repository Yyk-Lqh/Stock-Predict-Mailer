# 知识库与报告

CLI 的 `kb-*` 命令与 `/api/knowledge` 共用同一套私有知识库：原件加密保存在 `workspace/private-knowledge`，检索走 FTS5 关键词、可选 Embedding 与带有效期的关系表。命令行入口是兼容门面，只做三件事——把配置翻译成知识库身份、把入队翻译成同步、把证据还原成既有字段——不再维护第二套存储。因此 `kb-add` 支持 PDF/DOCX/TXT/Markdown/CSV/XLSX/JSON，需要 `knowledge` 可选依赖，并在命令返回前完成解析、清洗与建索引；失败时报错，不静默返回。

时间按「日」比较：`--published-at` 与 `--available-at` 的时分秒归入当天，检索按 `available_date <= 截止日期` 过滤。这是有意的精度让步，因为引擎本身按日比较；门面若改用更严格的小时比较，会出现「检索得到、校验却拒绝」的自相矛盾。需要小时级保守性的调用方，把 cutoff 前移一日再传入。

权限按 principal 隔离：同一份资料授权给 N 个 principal 时生成 N 份加密副本。`kb-revoke` 撤销该逻辑槽位下的全部副本，只停用、不删除原件，也不复活旧版本；硬删除需走 `DELETE /api/knowledge/documents/<id>`，不可恢复。principal 是受信本机命令行配置，不是可对外开放的身份认证服务，不能把当前 CLI 当作多租户安全系统。原文件、SQLite 与已导出的 HTML 仍需操作系统文件权限保护。

版本按逻辑槽位（源文件绝对路径的哈希）管理：同一槽位上传新版本时旧版本停用但保留，检索只在该槽位取「截止日可用且最新」的一个版本。因此 `--cutoff` 早于新版本可用日期时会回落到当时有效的旧版本——这是时点回放，而不是「永远只看最新版」。旧版 `state.sqlite3` 中的知识表已停用，仅作历史留档；它既不保存原件也不保存路径，无法据此重建，因此不提供迁移脚本。

报告明确区分输入事实、模型预测、资料原文、推断与未知项。所有标题和文档正文进行 HTML 转义，无网络脚本或远程资源。文档中的指令不会执行。当前未调用大模型，不能声称已实现完整生成式 RAG；后续接入需单独验收结构化输出、引用支持关系、外发白名单与失败降级。

```powershell
uv run stock-predict-mailer legacy --config config/local.toml kb-add path/to/note.md --published-at 2026-10-23T18:00:00+08:00 --available-at 2026-10-23T18:10:00+08:00 --allow owner
uv run stock-predict-mailer legacy --config config/local.toml kb-search "策略风险" --cutoff 2026-10-24T20:00:00+08:00
uv run stock-predict-mailer legacy --config config/local.toml report <experiment_id> --query "策略风险"
uv run stock-predict-mailer legacy --config config/local.toml kb-revoke <document_id>
```

`kb-*` 与 `report` 属于旧入口，须加 `legacy` 前缀（新默认入口只保留结果消费链路）；同样原因，这些命令需要 `.[research,trees]` 可选依赖。

## 批量导入

控制台一次传一份文件，种子库靠它灌不进去。批量入口在默认 CLI 上，不需要 `legacy` 前缀，也不依赖 `research/trees`：

```powershell
# 1. 按目录结构生成清单骨架，只写 CSV，不导入
uv run stock-predict-mailer --config config/local.toml knowledge-import data/inbox --write-manifest data/inbox/manifest.csv

# 2. 用表格填写来源、日期与标签（UTF-8 BOM，Excel 直接打开不乱码）

# 3. 试运行：打印计划与元数据，不写库
uv run stock-predict-mailer --config config/local.toml knowledge-import data/inbox --manifest data/inbox/manifest.csv --dry-run

# 4. 正式导入，并顺带处理队列
uv run stock-predict-mailer --config config/local.toml knowledge-import data/inbox --manifest data/inbox/manifest.csv --process
```

清单列为 `path,logical,source,document_date,available_date,valid_to,companies,industries,topics,stock_codes`，与 `metadata()` 的白名单一致；多值单元格用 `;`、`|`、`、` 或 `，` 分隔。出现未知列直接报错，不静默丢标签。

每一列填什么，以 `docs/知识库受控词表.md` 为准：8 个一级域与二级键、`logical` 第三级的命名规则、`topics` 的 30 个受控词、`industries` 的申万一级口径都在那里。词表外的写法视为录入错误——`logical` 带获取日期会让每次更新变成一份新资料，`topics` 自由生长会让标签退化成同义词垃圾场，两者都无法在事后修复。

四条约定：

1. **`available_date` 不静默取当天**。取值顺序为清单 → `--available` → `document_date`，三者皆无则该文件失败并说明原因；只有显式 `--assume-available-today` 才用当天，并计入 `warnings.available_date_inferred`。这个字段事后无法修复：把历史资料标成「今天可用」，回测就会让它提前生效。
2. **有清单时以清单为准**。未登记的文件跳过（不猜元数据），清单登记但文件不存在的报失败。因此清单本身就是一份可核对的入库台账。
3. **幂等按 `(logical, 内容哈希)`**。重复执行不会产生重复版本；内容变了则成为同一槽位的新版本，检索仍按截止日期选当时最新的一个。
4. **`logical` 留空时按目录推导**（`公告/甲公司/x.txt` → `公告/甲公司/x`）。文件名里带日期的，务必在清单里改写成不含日期的稳定槽位，否则每次更新都会变成一份新资料，而不是同一份的新版本。

导入只负责入队：不加 `--process` 时，仍需 `knowledge-worker --once` 或常驻 worker 处理。命令行的 principal 与控制台会话可能落在不同 owner 上，若控制台看不到刚导入的资料，用 `STOCK_PREDICT_MAILER_KB_KEY=<控制台密钥>` 重新导入；输出末尾的 `note` 会给出该 owner 的前缀，便于比对。有文件失败时命令返回码为 2。

## 队列与 worker 在线状态

控制台「资料与版本」页签顶部显示队列深度与清洗进程状态，数据来自 `GET /api/knowledge/queue`：该 owner 各状态的资料数、最近待办（失败与待审阅）、以及 worker 心跳。心跳存在 `workers` 表里——worker 是独立进程，SQLite 是它和控制台唯一共享的东西，所以存活状态必须落库而不是放内存。

四种显示对应四种处置：

| 显示 | 依据 | 该做什么 |
|---|---|---|
| 清洗进程在线 · 空闲 | 心跳在 90 秒内，`state=idle` | 无 |
| 正在处理 · `<资料名>` | `state=busy` | 大文件需要十几秒，正常情况不用管 |
| 清洗进程已退出 | 最后一次心跳是 `stopped` | 队列为空即正常；仍有排队就重新启动 |
| 无响应 · 最近心跳 x 前 | 超过 90 秒没有心跳，且未写 `stopped` | 进程被强杀或卡住，检查运行它的终端 |

「尚未在本机启动」与「无响应」刻意分开：前者需要给出命令（`uv run stock-predict-mailer knowledge-worker`，或加 `--once` 处理完即退出），后者需要去看进程。离线而队列里仍有资料时，状态条直接给出这条命令。

三点需要知道：

1. **被强杀时最多滞后 90 秒。** 正常退出与 Ctrl+C 都会走 `finally` 写 `stopped`，但 `kill -9`/任务管理器结束进程不会执行任何清理，此时只能等心跳过期。这是有意的取舍：宁可慢一拍报死，也不要因为一次慢写入就误报离线。
2. **`--once` 是一次性进程，跑完立刻显示已退出。** 它仍然会写 `stopped` 和本次处理的份数，所以「跑完即退」也能解释队列为什么不再推进——这比只显示「无进程」多一条线索。
3. **`processed` 是本次进程的计数**，重启归零；它不是累计入库数，累计数看列表的 `total`。

心跳写失败只吞掉异常，不影响本次导入：控制台看不到进度是显示问题，中断导入不是。`busy` 时只有正在处理的那份资料属于当前 owner，才显示名称，否则显示「其他资料」。

## 检索证据

「检索证据」页签提交 `POST /api/knowledge/search`，控制台只暴露常用五项：

| 字段 | 作用 | 不填时 |
|---|---|---|
| 查找证据 | 关键词，最长 4000 字 | 必填 |
| 截止日期 | 只用当天已可用的资料，决定「当时能看到什么」 | 今天 |
| 文档日期不早于 | 排除过旧资料；文档日期未知的条目一并排除 | 不限 |
| 股票代码 / 主体名称 | 规范化代码过滤；主体名称（全称或唯一简称）作为锚点把该主体的资料排在前面 | 不限 |
| 返回片段数 | 5 / 8 / 12 / 20 段 | 8 段 |

结果按版本槽位（`logical`）分组，每组标题给出文件名、文档日期、可用日期、有效期状态，以及「命中 N 段，显示 M 段」。分组不只是排版：

1. **一份长资料不该挤掉别的来源。** 选片先给每个版本一个名额，再按分数补齐剩余名额，`limit` 仍严格生效。少了这一步，一份几百页的年报可以占满全部 8 个名额，另一家公司的资料根本进不来。
2. **`命中 6 段，显示 1 段` 是「还有证据没取出」**，不是重复计数。要看更多原文就调大返回片段数，或补代码、日期把范围收窄。
3. **过期只标记、不排除。** 组标题写「已于 2026-09-30 失效」，条目同时给出「资料已过有效期，仅作历史参考」。时点回放常常正需要这类资料，直接隐藏会让当时的结论无从复核。
4. **命中版本多于返回版本时**，页面底部直接写明「另有 N 个版本命中」，避免误以为库里只有这几份。

参数错误按接口约定返回 400：`limit` 超出 1–20、日期不是 `YYYY-MM-DD`（Excel 常把 `2026-10-28` 存成 `2026/10/28`）。

### 别名：口语问，全称命中

检索是按字面匹配的：一份资料只有当它自己的写法与查询有重叠时才可能被召回。填表的人写「2026 年第三季度报告」「营业收入」，提问的人打「三季报」「营收」，两者一个字都不重合 —— 这时看到的「查不到」是**词表缺口**，不是索引故障。

`private_knowledge/aliases.py` 维护一张可评审的同义表，在查询侧补上规范写法：

| 提问 | 扩展出 | 说明 |
|---|---|---|
| `三季报` | `第三季度报告`、`三季度报告`、`Q3`、`3Q` | 报告期写法与季度编号 |
| `营收` | `营业收入` | 报表行名 |
| `归母净利` | `归属于母公司股东的净利润`、`归母净利润` | |
| `CPI` | `居民消费价格指数` | 宏观口径全称 |
| `降准` | `下调存款准备金率`、`存款准备金率` | |
| `产能利用率` | —— | **不收**：与「开工率」是两个口径，不是同义写法 |

三条设计约束：

1. **只扩查询，不动索引。** 资料始终按原文写法入库，所以 `aliases` 是纯查询期决定，加一条说法**不需要重新导入**，扩展也不可能凭空造出资料里没有的证据。
2. **单向扩展，组内第一个是规范写法。** `营收` 会带出 `营业收入`，`营业收入` 不会带出 `营收`——已经用规范写法提问时再加口语只会给排序添噪声。
3. **只收同义写法，不收上下位概念。** `产能利用率` 与 `开工率` 是两个口径，`降准` 与 `降息` 是两项政策；把它们当同义词，会把「问 A 答 B」变成静默行为——错命中比漏检更危险，因为漏检看得见。

响应里的 `aliases` 字段回显本次实际扩展了什么，页面在结果上方直接写「已按别名扩展查询：营收 → 营业收入」。看到这条提示时，命中的资料是按全称写成的，不是检索在猜。

改表之后要跑一次 `knowledge-eval`：别名会让某些旧用例的排序变化，只凭感觉判断「变准了」不足以证明。

### 实体锚定：先确定在问谁

70 份语料下，一条失败非常典型：问「该公司三季报营收同比增速」，前八位全是**别家**的季报。原因不是索引错了，而是排序只看关键词覆盖率 —— 另一家的标题重复了查询里的词，而真正要找的那张报表只重复了指标名。

锚定回答的是另一个问题：**这条片段属于谁**。问题里认得出的主体会变成一层排序：

| 来源 | 怎么认 | 例 |
|---|---|---|
| 查询里的股票代码 | `600000.SH` 这类规范代码 | 「600000.SH 三季报营收」 |
| 查询里的公司全称 | 与语料元数据里的公司名比对，可省略「股份有限公司」等后缀 | 「上海浦东发展银行 商誉减值」 |
| 显式参数 | `entity` 可传全称或简称；只有语料里恰好一家公司名包含它时才认 | 「三季报营收」+ `entity=浦发银行` |

三条边界：

1. **锚定是排序层，不是过滤器。** 除了显式 `entity`（它本来就表示「只要这家」），锚定的资料排在前面，别家的资料仍留在后面 —— 问题要的是「这家优先」，不是「只要这家」，因为顺带提到这家公司的证据往往正是下游证据。
2. **锚定靠元数据，不靠正文。** 报表切片里没有公司名，只有 `companies` / `stock_codes` 元数据知道它属于谁。关键词匹配永远连不上这种片段，锚定可以。
3. **指代不猜。** 查询里出现「该公司」「该产品」却没有任何锚点时，响应会带一条警告并说明「只按关键词排序」，页面同样显示。`knowledge-eval` 里的 q02/q14/q18 就是这个状态：问题本身没交代主体，检索没有义务替它编一个 —— q23 用同一句查询补上 `entity` 后立刻通过，这两件事必须分开看。

响应里的 `anchors` 回显本次锚定了什么、来自查询还是参数、牵涉几份资料；页面在结果上方写「已锚定主体：…」。解析简称失败时（例如语料里叫「中微半导体设备（上海）股份有限公司」，问题里写「中微公司」）不会静默降级，而是明确提示改用公司全称或股票代码。

### 汇总并回答

同一个表单里的「汇总并回答」走 `POST /api/knowledge/answer`，参数与检索完全相同。它**不是**大模型问答：没有配置聊天模型也会工作，内容是检索结果按固定顺序拼接的，`mode` 固定为 `evidence_extract`。

页面把结果拆成四段，顺序不能调换：

1. **关系证据**：`主体 —谓词→ 客体 · 有效期 · [片段]`。只有有效期覆盖截止日期的关系才会出现。
2. **条件性推断**：需要同时满足「主体是某公司的供应商」与「该供应商有停产、延期、短缺、制裁、火灾一类事件」，且关系与事件两侧都没有警告。每条推断都列出依据片段，并注明它不能用于量化损失——采购占比、影响范围、替代能力都不在证据里。
3. **冲突候选**：同一字段出现多个取值时全部列出，**不自动择一**。同主体、同周期、同单位而数值不同，说明来源之间有矛盾；周期或口径不同则只是标签没对齐。两者都不能靠挑一个数解决。
4. **需要注意**：逐条列出警告（文档日期未知、资料过期、事件时间未知、否定或不确定声明等）。

页面下方还有两个折叠项：`展开 N 段来源原文` 复用检索结果的分组视图，`纯文本（可复制进报告）` 给出接口返回的 `answer` 字符串。

三条边界要说清：

- **没有证据就不生成结论。** 检索为空时只说明「证据不足」并给出放宽条件的方向，不补造引用、不写推测。
- **推断不等于事实。** 界面文案固定标注「规则汇总，非模型生成」，因为把规则拼接的句子当模型结论引用，是本项目最容易出错的环节。
- **文本也会进报告。** `answer` 字符串用于粘贴到分析报告，所以它里面的每条摘录都带 `[document_id:ordinal]`，方便按引用回溯。

## 评测：把标注查询变成分数

「语料灌完了」和「问题能答上」是两件事。`knowledge-eval` 用一份标注用例集给检索打分，回答的是后者：

```powershell
uv run stock-predict-mailer --config config/local.toml knowledge-eval examples/knowledge-eval/cases.json --as-of 2026-11-15
```

退出码：`pass` 返回 0，其余（`fail` / `unsafe` / `empty`）返回 2，所以能直接放进流水线。用例文件不存在、字段拼错、`id` 重复同样是 2，并给出 `INVALID_INPUT`。

### 用例文件

顶层是 `{"version": 1, "cases": [...]}`，每条用例：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一；重复会直接中断 |
| `query` | ✅ | 检索词，1–4000 字 |
| `expect.logical` | ⚠️ | 期望命中的版本槽位，可只写前缀（`公告/600000.SH/`） |
| `expect.domains` | ⚠️ | 期望命中一级域，通常从 8 个域里选 1–2 个 |
| `expect.keywords` | 选填 | **全部**必须出现在返回片段里，用于校验「答案真的取到了」 |
| `expect.min_recall` | 选填 | 填了 `logical` 时默认 1.0；允许多槽位部分召回时调低 |
| `expect.relation` / `inference` / `conflict` | 选填 | 要求返回关系证据、条件性推断、冲突候选 |
| `as_of` / `start_date` / `stock_code` / `entity` | 选填 | 与检索接口同名同义 |
| `critical` | 选填 | 结构性硬指标：任一条失败，整轮直接 `fail` |
| `note` | 选填 | 给人看的备注，不参与计分 |

`expect.logical` 与 `expect.domains` 至少要填一个——两个都不填的用例永远通过，等于没有。

`examples/knowledge-eval/cases.json` 是种子库清单模板第八节那 20 条查询的机器可读版本，其中 3、6、7、20 标了 `critical`。**灌完库后要把真实槽位填进 `expect.logical`**：只靠域和关键词只能证明「检索跑对了方向」，不能证明取回了正确的那一份。

### 指标

| 字段 | 含义 |
|---|---|
| `totals.pass_rate` | 通过数 ÷ 参与评测数（**不含** `blocked`） |
| `metrics.mrr` | 第一个可接受结果的名次倒数；衡量「对的资料排第几」，不只是有没有 |
| `metrics.mean_recall` | 填了 `logical` 的用例平均槽位召回率 |
| `by_domain` | 按期望域分桶的通过率；一条用例声明两个域时两个桶各记一次 |
| `gates.safe` | 时点泄漏检查；任何一条返回片段的 `available_date` 晚于 `as_of` 即为 `false` |

`gates` 与通过率分开是刻意的：泄漏不是「质量差一点」，而是「这份回测无法复现」，所以它直接把结论改成 `unsafe`，而不是扣 0.1 分。

### 三种结果，对应三种修法

| 状态 | 含义 | 该改什么 |
|---|---|---|
| `pass` / `fail` | 语料里有，但没取到 / 取错 | 检索：查询词、`limit`、切片边界、索引 |
| `blocked` | 语料里没有该槽位，或活动版本还没到 `ready` | 语料：补文件、跑 worker、修清单 |

`blocked` 不计入通过率，因为「书架空了」和「索引坏了」的修法相反；把它算成失败，会让人去调检索参数而永远调不好。`blocked` 里会写明是 `absent`（根本没这份）、`pending`（还没清洗完）还是其他状态。

### 一个必须知道的局限

中文分词把**单字**也写进 FTS 索引，所以只声明 `domains` 的用例很弱：查「利率走廊」时，含「率」字的产业资料也会被召回，域判定照样通过。因此：

- 真实用例请至少带 `keywords`，或者直接写 `expect.logical`；
- 看到「域内通过率 100% 但业务方仍说查不准」，先怀疑用例太松，而不是检索太好。
- `expect.relation` 还多一个前提：**问题里必须出现实体**。关系图只从查询里出现过的 `subject`/`object` 向外扩散，写成「某公司」这类占位符时锚点为空，返回的 `relations` 一定为空（2026-11-15 试灌在 q07 上撞到）。
- 切片粒度同样影响关键词判定：`.txt`/`.md` 一行一片，且每个槽位先取最好的一片，「文档里有」不等于「结果里有」。段落内不要手动换行，关键段落里重复机制与指标全称。
- **语料一多，切片粒度不均就会变成排序偏差**：同样是 70 份资料，研报 docx 平均 15 片、PDF 整份只有 1 片，长文档在 Top-8 里挤占短文档。q03 的首位就是一份 PDF 公告，真正的研报被挤到第二。
- **口语别名没有映射**：「三季报」查不到只写了 `2026Q3` 的结构化报表，「营收」不等同于「营业收入」。这类漏检看起来像检索故障，实际是词表缺口，改的是别名表而不是索引。

2026-11-15 的两轮基线：10 份语料 20/20（MRR 1.00、槽位召回 1.00），70 份语料 17/20（MRR 0.95、槽位召回 0.85）。
前者只证明格式能解析，**后者才是有干扰项时的可用基线**。两轮的问题清单见 [试灌报告](试灌报告.md) 与 [语料扩容报告](语料扩容报告.md)。

评测本身不调用任何模型判分——判分是字符串匹配。模型做裁判会把方差加在最需要稳定的地方，而且同一份结果无法在两次运行间复现。

## 给 A2A Agent 开检索（可选）

外部 Agent 通过 `POST /a2a/<role>` 的 `knowledge/search` 方法检索同一个知识库，参数与 `/api/knowledge/search` 同名同义，另外多两个硬性条件：

1. **必须带 `X-Memory-Key`。** 知识库按 owner 隔离，而 A2A 的 Bearer 令牌只证明「能调这个服务」，不携带资料身份。所以带令牌不带密钥会被拒——这不是漏配，而是设计：宁可让对端拿到明确的 FORBIDDEN，也不要猜一个 owner 出来。
2. **必须给角色授权一级域。** 白名单为空即拒绝，默认状态就是全员无权限：

```powershell
# 查看现状（默认全部未授权）
uv run stock-predict-mailer --config config/local.toml knowledge-acl

# 允许 risk 角色读「研报」和「产业」两个一级域
uv run stock-predict-mailer --config config/local.toml knowledge-acl --role risk --domains 研报,产业

# 收回（传空字符串），该角色立刻失去读取权
uv run stock-predict-mailer --config config/local.toml knowledge-acl --role risk --domains ""
```

一级域取 `logical` 的第一段（`研报/中金公司/半导体设备跟踪` → `研报`），与 `docs/知识库受控词表.md` 的 8 个域一致。域名的合法性只校验格式（非空、无 `/`、≤20 字），不校验是否在词表内——写错的后果是永久查不到东西，因此返回体每次都会回显生效的 `domains`，对端和自己都能看见范围。

四条安全边界：

- **过滤发生在排名与截断之前。** 越权资料不占名额，`limit`、`logical_total`、`groups` 都只统计允许的版本。事后过滤会让「命中 8 条返回 2 条」变得无法解释。
- **不能靠参数越权。** 请求里带 `domains` 直接报 INVALID_PARAMS，白名单只能由 `knowledge-acl` 改。
- **拒绝优先于密钥校验。** 未授权角色无论密钥对错都先吃 PERMISSION_DENIED，避免用错密钥试探哪些域存在。
- **拒绝不返回空结果。** 空结果会被对端理解成「库里没有这份资料」，而不是「你没权限」——这两种情况在业务上完全不同。

调用示例（密钥来自控制台「创建或恢复访问密钥」）：

```powershell
$key = "<控制台记忆密钥>"
$body = '{"jsonrpc":"2.0","id":"1","method":"knowledge/search","params":{"query":"半导体设备 国产化","as_of":"2026-11-01","limit":5}}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8767/a2a/risk -ContentType application/json `
  -Headers @{ "X-Memory-Key" = $key } -Body $body
```

返回体在检索结果之外含 `role`、`effect: "read"`、`domains`，便于对端把「谁在什么范围里查到了什么」记进自己的审计。


HTML 与 JSON 生成于本地 workspace/reports；不进入 Git。数据年龄按自然日显式展示，演示的历史数据不伪装成当前行情。无符合条件资料时不补造引用。
